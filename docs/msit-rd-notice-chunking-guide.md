# R&D(기술개발) 공고 청킹/추출 가이드 (실측 기반)

2차 매칭(RAG) 설계를 위해 실제 저장된 과학기술정보통신부(MSIT, R&D·기술 카테고리) 공고문
300건을 직접 읽어서 검증한 결과다. AI팀이 청킹/임베딩 전략을 짤 때 참고용 자료로 남긴다.
아래 내용은 데이터 수집·검증만 담당(OCR/크롤링/외부 API 파트)한 실측 결과이며, 실제
청킹·임베딩 구현은 AI팀 영역(`app/ai/`, `app/services/matching_service.py`)이다.

## 1. 검증 방법

- 대상: `과학기술정보통신부` 소스로 수집된 공고 중 최신 300건
- 공고문 원문 선정: `app/services/msit_document_selector.py`(이미 병합됨)로 첨부파일
  여러 개 중 신청서식/안내서/매뉴얼/법령 등을 제외하고 실제 "공고문" 1개만 선택
- 텍스트 추출: 기존 OCR 파이프라인(`extract_text`, PDF/HWP/HWPX 지원) 재사용
- 청킹 실험: 섹션 제목처럼 보이는 줄(번호/기호로 시작 + 아래 키워드 포함)을 정규식으로
  찾아 그 지점 기준으로 문서를 자를 수 있는지 확인
- 표본을 100 → 200 → 300건으로 늘려가며 반복 검증 → 결과가 안정적으로 재현됨(아래 표)

| 표본 수 | 헤더 인식 성공률 |
|---|---|
| 100건(기술개발+자금 혼합) | 89% |
| 200건(기술개발만) | 93.5% (187/200) |
| 300건(기술개발만) | 93.7% (281/300) |

표본을 늘려도 비율이 흔들리지 않아 이 방식이 안정적이라고 판단.

## 2. 추출 우선순위 (섹션 등장 빈도, 300건 기준)

| 순위 | 섹션 | 등장 횟수 | 매칭 관점에서의 의미 |
|---|---|---|---|
| 1 | 신청자격 | 384 | 자격요건 — 매칭 핵심 |
| 2 | 선정평가 | 355 | 선정기준 — 매칭 핵심 |
| 3 | 신청방법 | 331 | 절차성, 매칭엔 덜 중요 |
| 4 | 문의처 | 317 | 절차성, 매칭엔 불필요 |
| 5 | 신청기간 | 295 | 이미 별도 필드(`application_end_date`)로 구조화되어 있음 |
| 6 | 제출서류 | 249 | 절차성 |
| 7 | 사업개요 | 225 | 지원내용 — 매칭 핵심 |
| 8 | 지원내용 | 222 | 지원내용 — 매칭 핵심 |
| 9 | 사업목적 | 192 | 지원내용 — 매칭 핵심 |
| 10 | 지원대상 | 115 | 자격요건 — 매칭 핵심 |
| 11 | 지원규모 | 66 | 지원내용 보조 |

**권장**: 임베딩 비교 대상은 `신청자격 + 지원대상 + 사업개요/사업목적/지원내용 + 선정평가`로
좁히고, `신청방법/문의처/제출서류`는 청크는 만들되 매칭 스코어링에는 제외하는 것을 추천.
누가 받는지·뭘 받는지·어떻게 뽑는지가 매칭에 실질적으로 쓰이는 정보이고, 나머지는 절차
안내라 문서마다 표현만 다를 뿐 매칭 신호가 거의 없음.

## 3. 청킹 알고리즘 (실측 검증된 방식)

방식: 줄 단위로 순회하면서 "번호/기호(□○◎Ⅰ~Ⅴ 등)로 시작하고 아래 키워드를 포함하는
30자 이하의 짧은 줄"을 섹션 헤더로 간주 → 그 지점부터 다음 헤더 전까지를 한 청크로 묶는다.

```python
_SECTION_KEYWORDS = [
    "사업개요", "사업목적", "지원대상", "지원내용", "지원규모",
    "신청자격", "신청제한", "제외대상", "지원 제외", "지원제외",
    "신청기간", "신청방법", "제출서류", "구비서류", "신청·접수", "신청 접수",
    "선정평가", "선정절차", "문의처",
]
_HEADER_PATTERN = re.compile(
    r"^\s*(?:[0-9]{1,2}[.\)]\s*|[□○◎ⅠⅡⅢⅣⅤ]\s*)?(" + "|".join(_SECTION_KEYWORDS) + r")"
)
```

각 줄에 대해 `len(stripped) <= 30`이고 위 패턴에 매치하면 헤더로 인식. 헤더가 하나도
안 잡히는 문서(6.3%)는 통째로 하나의 청크로 폴백 처리하는 게 안전.

**주의**: HWP/HWPX/PDF를 텍스트로 뽑으면 표(테이블)가 셀 단위로 줄바꿈되면서 `5`, `25`
같은 순수 숫자 줄이 다수 생긴다. 이건 페이지 번호나 표 값이지 헤더가 아니므로, 헤더
후보를 찾을 때 순수 숫자만 있는 줄은 반드시 제외해야 노이즈가 안 낀다(실측 확인).

## 4. 키워드 목록에 추가하면 좋을 후보 (누락분)

위 청킹 키워드 목록에 없어서 못 잡았지만, 300건 중 상당수(30~98회)에서 반복 등장한
헤더 후보들이다. 실측으로 재현성 있게 나온 것만 추렸다.

**공통적으로 자주 나오는 것 (추가 추천)**
- 기타사항 / 특기사항 (98회 / 30회)
- 신청 시 유의사항 / 유의사항 (93회 / 39회)
- 사업 내용 / 사업내용 — 띄어쓰기 변형, `지원내용`과 별도로 쓰이는 경우가 많음 (90회 / 33회)
- 사업 개요 — `사업개요`의 띄어쓰기 변형 (32회)
- 적용 법령 및 규정 (58회)
- 평가절차 / 평가방법 — `선정절차`/`선정평가`의 동의어 표현 (44회 / 38회)
- 향후일정(안) (40회)
- 문의 절차 / 공고문 및 양식 확인 방법 — `문의처`류 (97회 / 98회)
- 신청 제한사항 — `신청제한`의 띄어쓰기 변형 (75회)

**R&D(기술개발) 특유의 세부 항목 (일반 공고엔 잘 안 나옴)**

이 항목들은 이름만 봐서는 뭘 담고 있는지 알기 어려워서, 실제 내용과 매칭 관점에서
쓸모가 있는지를 하나씩 풀어썼다. 정리해보면 세 그룹으로 나뉜다.

**(A) 사실은 매칭에 쓸 수 있는데, R&D 특유 용어로 포장돼 있을 뿐인 항목**
→ 기존 매칭 필드에 그냥 합쳐서 취급하면 됨.

| 세부 항목 | 실제 내용 | 어디에 합칠지 |
|---|---|---|
| 연구개발목표 (30회) | 이 과제로 달성하려는 구체적 기술 목표/성능치(예: OO기술 TRL 5 달성) | `사업목적`/`지원내용`과 같은 성격 — 합쳐서 취급 |
| 추진배경 (29회) | 정부가 왜 이 사업을 하는지(정책 배경, 산업 현황) | `사업개요`와 같은 성격 |
| 정부지원연구개발비의 지원기준 / 기관부담연구개발비의 부담기준 (31/31회) | 정부가 얼마를 대주고 기업이 얼마를 자체 부담해야 하는지(기업 규모별 매칭펀드 비율) | `지원규모`의 세부 조건 — 회사 규모(대/중견/중소)에 따라 달라지는 실제 지원율 정보라 매칭에 유용함 |
| 가감점 제도 (32회) | 특정 조건(여성기업, 지방소재 등) 충족 시 평가에 가점/감점 부여 | `선정평가`의 보너스 조건 — 매칭 스코어링에 참고할만함 |

**(B) 선정 이후 행정/재무 의무사항 — 매칭과 무관, 신청 전 자격요건이 아니라 선정된 후 지켜야 할 규정**

| 세부 항목 | 실제 내용 |
|---|---|
| 기술료 납부에 관한 사항 (78회) | 지원받아 개발한 기술로 나중에 돈을 벌면, 그 수익의 일부를 정부에 "기술료"로 반납해야 한다는 사후 정산 규정 |
| 연구개발과제의 성실 수행 (84회) | 목표를 100% 달성 못해도 "성실하게 수행했다"고 인정되면 실패로 안 보는 판정 기준 — 과제 종료 후 평가 방식에 대한 규정 |

**(C) 순수 서식/행정 규칙 — 매칭과 전혀 무관, 참고용 원문으로만 남기면 됨**

| 세부 항목 | 실제 내용 |
|---|---|
| 사업수행체계 및 용어 (66회) | 컨소시엄 구성 시 "주관기관/참여기관/위탁기관" 같은 용어 정의 — 일종의 용어집 |
| 연구개발계획서 분량 제한 (63회) | 제출 서류는 몇 페이지 이내로 작성하라는 서식 규칙 |
| 연구과제 상세 계획 (29회) | 계획서에 어떤 항목을 어떤 순서로 써야 하는지 안내(서식 가이드) |
| (필수) 연구데이터 관리 / 데이터 개요·수집·가공 (65회, 31~33회) | "데이터 구축형" 과제에 한해, 수집할 데이터 종류·관리계획을 제출하라는 정부 데이터정책 준수 요건 |
| (해당시) 젠더혁신 관점 연구 (29회) | 보건/사회 분야 연구 시 성별 차이를 연구설계에 반영하라는 정책 요건(해당하는 과제에만 적용) |

## 5. 제안

1. 위 "공통적으로 자주 나오는 것"(4장 첫 목록)은 `_SECTION_KEYWORDS`에 그대로 추가해도
   안전함 — 일반 공고 문서에도 자연스럽게 등장하는 절차성 표현들.
2. **(A) 그룹은 새 카테고리를 만들지 말고 기존 매칭 필드(사업목적/지원내용/지원규모/선정평가)에
   합쳐서 청킹**하면 됨 — 이름만 R&D식일 뿐 매칭 관점에서 하는 역할은 동일함.
3. **(B), (C) 그룹은 매칭용 임베딩·스코어링 대상에서 아예 제외**하는 걸 추천 — 신청
   자격이나 지원 내용이 아니라 "선정된 다음에 지켜야 할 규정"이거나 "서류 작성 형식"이라
   기업이 이 공고에 지원할지 말지 판단하는 데 도움이 안 됨. 다만 사용자가 공고 원문
   전체를 읽고 싶을 수 있으니, 매칭용 벡터에는 안 넣되 원문 텍스트 자체는 그대로 보존.
4. 청크에 태그(예: 섹션명 + A/B/C 그룹)를 함께 저장해두면, 나중에 "신청자격 청크끼리만
   비교" 같은 섹션별 비교도 가능해짐 — 문서 전체를 통째로 임베딩하는 것보다 정밀한 매칭이
   될 것으로 기대됨(구체적 구현 방식은 AI팀 결정 사항).
